GK Trucking Services 2.0 — Build phases

Approach
- Backend first, then UI, per feature (test each piece before the next).
- MVP (first serious demo) = checkpoint B: full trip + EIR/POD + unpaid/paid invoice.
- After MVP: map, emails, ratings, activity logs, earnings charts.
- UI page polish priority by role: Admin → Staff → Driver → Customer (F3–F6).
- Frontend foundations (F1–F2) before role-specific polish; see development_notes.txt “UI”.
- Remind to add env keys when each phase needs them (see env_checklist.txt).
- External APIs (Mail, Mapbox): placeholders first — stub services,
  no live calls until keys are set. See development_notes.txt.
- PayMongo: cancelled / not in scope.
- E-payment: QR Ph (InstaPay P2M) — Metro Manila static merchant QR; not a PayMongo gateway.

Status legend: [ ] pending · [x] done

Checkpoints
- A: Customer books → gatepass → driver delivers → EIR/POD → completed
- B (MVP): A + invoice unpaid/paid
- C (post-MVP): Mapbox route, emails, ratings, logs, earnings overview

Brand
- Product name: GK Trucking Services
- Booking numbers: GK-{YEAR}-%04d (dynamic year, Asia/Manila)

[x] B1. Auth
- Unified users + roles (customer, driver, staff, system_admin)
- Shared login → redirect by role
- Customer/Driver register + email verification (auto-active)
- Admin creates Staff (and any role)

[x] B2. Admin master data
- Settings, Pricing List, Fleet, User management (policies + CRUD; archive on delete)
- Routes: /admin/settings, /admin/pricing, /admin/fleet, /admin/users

- UserSeeder: plain passwords (hashed via model cast)

[x] B3. Customer bookings (data + rules)
- Create / list / details; fare from Pricing, locked on Invoice.amount at issue
- Pickup/dropoff address + lat/lng
- Rules: pricing row exists; at least one available fleet unit of type; GK-{YEAR}-#### via booking_seq
- Routes: /customer/bookings (index, create, store, show); BookingPolicy + CreateCustomerBooking action
- Minimal customer layout (F6 polishes customer UI)

[x] B4. Staff/Admin bookings + gatepass
- Staff: update fields, status/cancel only before gatepass; first gatepass upload
- Admin: full CRUD, gatepass override, archive

[x] B5. Driver deliveries
- Available (gatepass + matching vehicle type), one active, accept, status updates
- Vehicle in_use / release

[x] B6. EIR + POD
- Required both before completed

[x] B7. Invoice (MVP end)
- One per booking; unpaid / paid; Staff + Admin mark paid

→ Checkpoint B (MVP)

[x] B8. Mapbox helpers (post-MVP)

FRONTEND PHASES (backend B0–B10 complete; UI from F1 onward)

[x] F1. Layout shells + shared UI components
    - Theme tokens in resources/css/app.css (Tailwind v4 @theme): mock primary #2596be
      with tint/shade/tone scale + neutral palette for easy rebrand (no final branding yet).
    - Three layouts: auth (sign-in/sign-up/verify only); management (Admin + Staff);
      portal (Customer + Driver). Thin role wrappers may extend management/portal.
    - Management: collapsible left sidebar + top bar (user, logout). Portal: top bar +
      card-based pages (mobile-friendly). Wire @vite on all layouts; Alpine.js via Vite
      (sidebar toggle; later uploads/signature in F7+). Lucide icons via npm + <x-ui.icon>.
    - Shared Blade components under resources/views/components/ui/ (button, input,
      badge, card, flash, page-header, table shell, etc.). Domain partials stay in
      resources/views/bookings/ (_invoice, _rating, _route_map, etc.).
    - Views stay role-first at top level: admin/, staff/, driver/, customer/ (no mass
      rename to feature/role nesting).
    - Replace inline <style> in current layouts/admin|staff|driver|customer stubs.

[x] F2. Auth pages (dedicated auth layout — not management/portal shells)
    - Login, register customer/driver, verify email (B1 stub forms exist for QA).
    - Real mail send still awaits MAIL_* / GK_MAIL_ENABLED — development_notes.txt

[x] F3. Admin UI (first role polish): settings, pricing, fleet, users, bookings,
    earnings, activity logs (beyond B2/B4/B10 stubs)

[x] F4. Staff UI: overview, bookings list/show, gatepass upload

[x] F5. Driver UI: overview, deliveries available / active / show, settings

[x] F6. Customer UI: overview, My Bookings, new booking, booking details

[x] F7. Document upload/view UI (gatepass, EIR, POD — ACL streamed routes)
    - Shared bookings._documents_panel with inline previews (customer / driver / staff / admin)
    - ACL streamed document routes unchanged; uploads reuse _eir_pod_upload

[x] F8. Invoice UI (unpaid/paid; Staff/Admin mark paid)

[x] F9. Map on booking details (after accept)
    - Interactive Mapbox route on customer / driver / staff / admin booking details whenever pickup and dropoff coordinates exist (zoom out 8, zoom in 17)
    - Staff overview includes the same active-booking route map as admin
    - Customer and admin create: one map to search or click pickup and dropoff (Mapbox Geocoding)
    - Requires MAPBOX_TOKEN (or MAPBOX_ACCESS_TOKEN) + GK_MAPBOX_ENABLED=true

[x] F10. Ratings, activity logs presentation, earnings/overview charts
    - Customer star rating UI; staff/admin booking show displays ratings
    - Activity logs: date range, location/geo/properties expand, login geo (best-effort)
    - Optional IP location via GK_ACTIVITY_IP_LOOKUP; admin overview keeps KPI snapshot + link to earnings charts

[ ] F11. QR Ph (InstaPay) e-payment for invoices
    - PayMongo out of scope. Use BSP QR Ph person-to-merchant (P2M) over InstaPay rails
      (common Metro Manila merchant QR: GCash / Maya / bank apps scan one code).
    - Static company QR from GK’s bank or EMI (Settings upload); show on unpaid invoice
      with amount; customer enters amount in their app after scan.
    - No direct InstaPay ACH integration in-app (requires licensed PSP). Staff/Admin still
      mark invoice paid after verifying bank/SMS (optional: customer reference or proof).
    - UI wording: prefer “Pay via QR Ph (InstaPay)” over generic “InstaPay QR” (avoids P2P confusion).
