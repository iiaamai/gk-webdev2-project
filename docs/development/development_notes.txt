GK Trucking Services 2.0 — Development notes

Purpose
- Track decisions that affect how phases are built (especially external APIs).
- Source of truth for “placeholder until enabled” integrations.
- Related: phases.txt, env_checklist.txt.

Policy (agreed)
- Backend before frontend, per feature.
- Phases that need external APIs ship as placeholders first: stub service
  classes/methods that return null / “not configured” and never call the API.
- Live calls only after the matching env keys are added (see env_checklist.txt).
- Agent/dev must remind the user which keys to add when enabling an integration.

---

UI (frontend — decided before F1)

Purpose
- Single place for shells, theming, view/component conventions. Details per phase in phases.txt F1–F10.

Build priority (role polish)
- Admin → Staff → Driver → Customer (phases F3 → F4 → F5 → F6).
- F1–F2 (tokens, shells, auth) apply to all roles before F3+.

Stack
- Tailwind CSS v4 via Vite (resources/css/app.css).
- Alpine.js via Vite for light interactivity (management sidebar toggle; later F7+ flows).
- Blade only (no SPA); prefer named routes and route() in nav.

Theming (mock brand until real branding)
- Mock primary: #2596be as --color-primary (utilities: bg-primary, text-primary).
  Named steps in app.css @theme (no primary-50…950 scale):
  primary-tint-1..3 (lighter; 1 = subtle), primary-shade-1..3 (darker; 1 = subtle),
  primary-tone-1..3 (muted/desaturated surfaces and borders; 1 = subtle).
- Neutral scale (slate/zinc-style) for surface, border, body/muted text.
- Semantic aliases in @theme where useful (e.g. surface, border, text-muted) so
  Blade uses utilities, not hardcoded hex. Rebrand = edit app.css tokens only.

Layouts (three shells)
1. auth — login, register customer/driver, verify email (centered card; no portal/management chrome).
2. management — Admin + Staff: collapsible left sidebar + top bar (user, logout).
   Staff nav is a subset of Admin (permissions already in policies).
3. portal — Customer + Driver: top bar + card-based content, mobile-first.

Role layout files
- May keep layouts/admin.blade.php, staff, customer, driver as thin @extends wrappers
  on management or portal so existing @extends paths need minimal churn.
- Shared chrome partials: e.g. layouts/partials/ (sidebar, topbar, portal header, flash).

View folders
- Role at top level: resources/views/{admin,staff,driver,customer}/...
- Cross-role booking markup: resources/views/bookings/_*.blade.php partials.
- Do not nest feature/role (e.g. bookings/admin/) unless a future refactor is agreed.

Shared components
- Generic UI in resources/views/components/ (Blade <x-ui.*> or project convention):
  button, input, select, textarea, label, field-error, badge, card, page-header,
  flash, table shell, empty-state.
- Domain-specific pieces stay in role views or bookings/ partials, not generic components.

Vite
- All layouts must @vite resources/css/app.css and resources/js/app.js (welcome.blade.php
  already does; B-era stubs used inline CSS until F1).
- If styles do not appear, run npm run dev or npm run build.

Auth UI (F2)
- Dedicated auth layout only; not management or portal shells.
- Email verification UI ships in F2; GK_MAIL_ENABLED=false behavior unchanged from B1.

Placeholder integrations

1. Mail (Laravel Mail / SMTP)
Status: placeholder until enabled
Phases: B1 (email verification), B9 (event emails), F2 (verify UI)
Env when enabling: MAIL_MAILER, MAIL_FROM_ADDRESS, MAIL_FROM_NAME
  (and SMTP/Mailtrap host keys if not using log)
Notes
- Do not send real email until this is enabled.
- Stub / no-op mail path during early backend; verification and notification
  flows can exist as code paths that skip send or mark “not configured”.
- When enabling: wire Laravel Mail + events in email_events.txt.

2. Mapbox
Status: placeholder until enabled
Phases: B8 (helpers), F9 (map on booking details); settings map_center_* keys
Env when enabling: MAPBOX_TOKEN (or MAPBOX_ACCESS_TOKEN)
Notes
- Stub Mapbox/route helper: return null / “not configured”; no HTTP to Mapbox.
- Booking still stores pickup/dropoff lat/lng for later use.
- When enabling: static optimal route from coords only (no live GPS).

3. PayMongo
Status: placeholder until enabled (after MVP B)
Phases: reserved on Invoice (paymongo_reference); online pay after checkpoint B
Env when enabling: PAYMONGO_SECRET_KEY, PAYMONGO_PUBLIC_KEY
Notes
- MVP uses Pay Later only (invoice unpaid / paid). No PayMongo API calls.
- Stub payment service if scaffolded early; keep DB field nullable.
- When enabling: field mapping + webhooks (see missing_dev_contents item 12).

Enable checklist (per integration)

1. Add env keys from env_checklist.txt (never commit secrets).
2. Replace stub methods with real client/API calls.
3. Update this file: Status → enabled; note date if useful.
4. Smoke-test the related phase (B1/B9, B8/F9, or PayMongo slice).

Before starting (pre-B0 recommendations)

1. Env first (foundation only)
- Set APP_NAME, APP_KEY, APP_URL, timezone Asia/Manila, DB_CONNECTION=sqlite.
- Do not add MAIL_*, Mapbox, or PayMongo keys until those integrations are enabled.

2. B1 email verification while Mail is placeholder (decide before coding auth)
- DECIDED (B1): Option A + auto-verify on register while GK_MAIL_ENABLED=false.
  Seeds and new customer/driver/admin-created users get email_verified_at set.
  Verify routes exist; sendEmailVerificationNotification is a no-op until Mail enabled.
- When enabling Mail: set GK_MAIL_ENABLED=true and MAIL_* keys; new registers may
  leave email_verified_at null and use real verification emails.

3. Extend stock users migration in B0
- Default Laravel users table lacks role, mobile, driver fields, archived_at.
- B0 should alter or replace that migration to match docs/development/models/user.txt.
- Fresh SQLite migrate is fine at this stage.

4. One slice at a time
- B0 scope: migrations + Eloquent models + seeders only.
- Do not mix B1 auth UI or portal routes into the same pass.

5. Auth stack (decide at B1, not B0)
- DECIDED (B1): Manual controllers + Form Requests (not Breeze), so portal
  prefixes (/customer, /driver, /staff, /admin) stay first-class in routes/web.php.

6. Soft archive (optional but useful in B0)
- Shared archived_at pattern + global scope (or query helper) so normal lists
  hide archived rows by default.

7. Seed sample bookings (B0)
- Follow seed_plan.txt: multiple statuses (pending w/o gatepass, pending with gatepass,
  accepted, in_transit, completed with EIR/POD, cancelled) so lists/overview are
  testable after early UI slices.

What is still “real” vs placeholder

Real (not dummy)
- Laravel auth: hashed passwords, roles, middleware, role-based redirect.
- Seeded demo users (seed_plan.txt) are sample data, not fake “pretend login”.
- Full booking lifecycle, gatepass, accept, vehicle lock, EIR/POD, Pay Later invoice.
- Policies, Form Requests, private document ACL, portal CRUD + Blade UI.

Placeholder until user enables external API
- Mail: no real send (verify/notification code paths may exist as stubs).
- Mapbox: no route/map HTTP calls.
- PayMongo: Pay Later only; no online payment API.
