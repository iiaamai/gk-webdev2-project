GK Trucking Services 2.0 — Driver Time-In / Time-Out plan
============================================================
Status: design agreed (clarify session) — implement when explicitly requested (/implement).
Scope: MVP / checkpoint B (phases.txt).

Process flow (office + driver)
------------------------------
1. Request for Time-In: The driver informs the office (Admin or Staff) that they are ready to time in.
2. Office processes Time-In: Admin or Staff records Time-In in the system.
3. Driver login access: Once Time-In is recorded, the driver may log in.
4. Request for Time-Out: After duty, the driver informs the office they are ready to time out.
5. Office processes Time-Out: Admin or Staff records Time-Out in the system.
6. Driver login restriction: After Time-Out, the driver cannot log in until timed in again.

Driver requests are offline only (phone, radio, desk) — no in-app “request time-in/out” buttons in v1.

Technical flow
--------------
Driver requests Time-In from office (offline)
  → Admin or Staff records Time-In
  → System marks driver as timed in
  → Login allowed (new sessions)

Driver completes duty; requests Time-Out (offline)
  → Admin or Staff records Time-Out (blocked if active trip — see rules)
  → System marks driver as timed out
  → Login restricted (new sessions only; existing session unchanged)

Login validation (drivers only)
- Timed in  → login permitted (after normal auth: password, email verified, not archived).
- Timed out or never timed in → login denied with clear office-oriented message.

Current behavior (baseline)
---------------------------
- Drivers self-register, verify email, and log in when credentials are valid and account is not archived.
- app/Http/Requests/Auth/LoginRequest.php — no attendance check today.
- No Time-In / Time-Out data model or Staff/Admin UI.

Locked product decisions (clarify)
----------------------------------
| Topic | Decision |
| When | MVP / checkpoint B |
| Who records | System Admin + Staff |
| No attendance record yet | Login denied until first Time-In |
| Time-Out during trip | Block Time-Out if driver has accepted or in_transit booking |
| Time-Out + active session | Block new logins only; do not force logout mid-session |
| Same calendar day | Unlimited Time-In / Time-Out cycles |
| Driver request UI | Offline only — office records in portal |

Rules (detail)
--------------
Attendance states (driver-facing login gate)
- Not timed in (includes never timed in): login denied.
- Timed in: login allowed.
- Timed out: login denied until office records a new Time-In.

Time-In
- Staff or Admin action on a driver user (driver role only).
- Sets current state to timed in; append audit/history row (who, when, Asia/Manila).

Time-Out
- Staff or Admin action on a driver who is currently timed in.
- Rejected if driver has any booking in accepted or in_transit status (vehicle still on active trip).
- Sets current state to timed out; append audit/history row.
- Does not invalidate an existing driver portal session — only blocks the next login attempt.

Permissions
- Staff and Admin may record Time-In and Time-Out (same capability for this feature).
- Customers and drivers cannot record attendance for themselves in v1.

Implementation hints (when building)
------------------------------------
Data
- Prefer driver_attendance_logs (or equivalent) with timed_in_at, timed_out_at, recorded_by user_id,
  plus a derived “current status” on the driver (query latest open shift or status column on users for drivers).
- Timestamps in Asia/Manila; align with existing activity log patterns if desired.

Backend
- Action or service: TimeInDriver, TimeOutDriver (validate role, state transitions, active booking check on time-out).
- LoginRequest::authenticate() (or small helper): after Auth::attempt, if user is driver and not timed in, logout + validation message.
- Optional: activity log entries for time-in/out (post-MVP nice-to-have if not in first slice).

UI
- Staff + Admin: driver list and/or driver detail — show attendance status, Time-In / Time-Out buttons, flash errors for blocked time-out.
- Driver portal: no new buttons; login form shows message when denied for attendance.

Tests (feature)
- Driver denied login before first time-in; allowed after staff/admin time-in.
- Driver denied login after time-out; allowed again after second time-in same day.
- Time-out blocked when driver has accepted or in_transit booking.
- Time-out does not require force logout (assert session still works on driver route if already logged in — product choice).
- Non-drivers (customer, staff, admin) unaffected by attendance gate.

Suggested implementation order
------------------------------
1. Migration + model(s) + status helper for “is driver timed in”.
2. TimeIn / TimeOut actions + policies (staff/admin, driver target).
3. Staff/Admin UI on drivers.
4. Login gate in LoginRequest + feature tests.
5. Seed/demo note: demo drivers need Time-In before driver login on fresh DB (document in seed_plan or seeder).

Out of scope (this plan)
------------------------
- In-app driver “request time-in/out” or admin notifications.
- Force logout or stop GPS updates on time-out (explicitly not in v1).
- One shift per day limits; payroll / hours reporting; geofenced time-in.
- Attendance for non-driver roles.
- Changing fleet map or booking lifecycle beyond time-out guard on active trips.
